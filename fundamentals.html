Foundations

SRE fundamentals

The core ideas from Google's Site Reliability Engineering book and The Site Reliability Workbook, updated with modern practice and applied to an LLM-backed product.

  • Reliability is measured from the user's point of view with SLIs, targeted with SLOs, and spent through an error budget.
  • For LLM features, time to first token, throttle rate, and content-filter rate matter as much as classic latency and errors.
  • Alert on error-budget burn rate, not raw thresholds. Learn from incidents with blameless postmortems.
For senior managers · reliability is a business decision

Your role

  • Set reliability targets (SLOs) together with product. Engineering shouldn't guess.
  • Back the error budget policy, even when it means pausing a launch.
  • Keep toil visible, and fund the work to automate it away.

Questions to ask

  • What's our SLO for each key feature, and are we meeting it?
  • How much error budget is left this month?
  • What happens when the budget runs out, and will we actually do it?
  • How much of the team's time goes to repetitive manual work?

Avoid

  • Asking for "five nines" without knowing what it costs.
  • Treating SLO misses as performance problems for individuals.

100% is the wrong target

Google's SRE book argues that aiming for perfect reliability is a mistake. Users can't tell 99.99% from 100% because their Wi-Fi, laptop, and the model itself are less reliable than that. Every extra nine costs a lot and slows feature work. The job is to pick the right level of reliability for each feature, then spend whatever is left over deliberately.

Applied to Nimbus

Writing Assist is interactive and used constantly, so it deserves a tight target. Proactive Tips runs in the background and retries quietly, so a looser target is fine. Giving them the same target wastes effort on one and short-changes the other.

SLIs, SLOs, and error budgets

SLI: indicator

A measurement of user experience, expressed as good events ÷ valid events. Example: the share of Writing Assist requests that succeed.

SLO: objective

A target for an SLI over a window. Example: 99.5% of requests succeed over 28 days.

Error budget

The allowed unreliability, 1 − SLO. At 99.5%, 0.5% of requests may fail. Spend it on launches and experiments, not on surprises.

An error budget policy spells out what happens when the budget runs out. A typical policy freezes risky launches for that feature and moves the CFT onto reliability work until the budget recovers. Without a written policy, an SLO is just a number on a slide.

The four golden signals

If you can only monitor four things, the SRE book says to monitor these. Here's what each one means for Nimbus:

SignalClassic meaningIn Nimbus
LatencyHow long requests take. Track successes and failures separately.End-to-end duration, time to first token, and Foundry dependency duration. Use percentiles, never averages.
TrafficDemand on the systemRequests per feature, and tokens per minute, which is what quota is actually measured in.
ErrorsRate of failed requests5xx, 429, timeouts, content-filter blocks, plus "successful" responses that are empty or malformed.
SaturationHow full the system isPTU utilization, tokens per minute against quota, APIM capacity, and service CPU or thread pools.
Averages lie

If the average latency is 2 s, the P99 could still be 25 s. LLM latency is long-tailed because it depends on output length. Use P50, P95, and P99, and remember sampling: weight counts by itemCount.

LLM-specific signals

Generative AI adds failure modes that classic web metrics miss:

Time to first token (TTFT)

How long until the first streamed token arrives. This shapes how fast the product feels. High TTFT usually means queueing or capacity trouble.

Tokens per second

Generation speed once streaming has started. If it drops, the model or deployment is under pressure.

Throttle rate (429)

The share of calls rejected for quota. On shared deployments one CFT can exhaust quota for everyone.

Token usage

Input and output tokens per request. When prompts quietly grow, latency and cost rise and quota runs out sooner.

Content-filter rate

Responses blocked by safety filters. A spike can follow a prompt change or a policy change.

Quality

Groundedness and task success, measured with offline evaluations and user feedback. A fast, wrong answer still counts as an incident.

Alert on burn rate, not thresholds

"Error count > 50" pages you at 3am for a blip and stays quiet during a slow leak. The Site Reliability Workbook recommends multi-window, multi-burn-rate alerts. Burn rate is how fast you're using the error budget compared with spending it evenly: burn rate = observed error rate ÷ (1 − SLO).

An alert fires only when both windows are over the threshold. The long window shows the problem is significant, and the short window shows it's still happening. With a 99.5% SLO, a 14.4× burn means an error rate of about 7.2%. The query library has a burn-rate query you can adapt.

Monitoring vs observability

Monitoring answers questions you predicted ("is the error rate above X?"). Observability lets you answer questions you didn't predict ("why are only 4.12 clients in Sweden slow on Device Care?"). You need high-cardinality, correlated telemetry for that: traces with rich attributes, not just pre-aggregated counters.

OpenTelemetry in one minute

  • Traces follow one request across services. Each hop is a span, and spans share a trace ID, which App Insights calls operation_Id.
  • Context propagation passes the trace ID between processes in the W3C traceparent header. If one hop drops it, the trace breaks.
  • Metrics are cheap aggregates for dashboards and alerts. Logs are detailed events, ideally tagged with trace IDs.
  • Semantic conventions standardize attribute names. The GenAI conventions define attributes such as gen_ai.request.model and gen_ai.usage.input_tokens, so every CFT's model calls look the same in queries.
  • Resource attributes such as service.name identify where telemetry came from. In App Insights service.name becomes cloud_RoleName. Getting it right is the cheapest maturity win there is.

Toil

The SRE book defines toil as work that is manual, repetitive, automatable, reactive, and without lasting value, and that grows as the service grows. Google caps toil at 50% of an SRE's time. In Nimbus, typical toil includes hand-running the same KQL at every incident, restarting stuck pods, and manually mapping alerts to owners. Each of these is a candidate for a saved query, a dashboard, or an automation.

Blameless postmortems

Write a postmortem for every Sev 1 and Sev 2, and for any incident that taught you something. Blameless means assuming everyone acted reasonably given what they knew at the time, and asking how the system made the failure possible rather than who caused it. The output is a set of owned, tracked action items, not a document that sits in a folder.

Safe change

Most incidents start with a change. The SRE book's advice still holds: use progressive rollouts, detect problems quickly, and roll back safely. For Nimbus that means:

  • Staged client rollouts (1% → 10% → 50% → 100%) with automatic halts on crash or error spikes for the new version.
  • Feature flags for prompt templates and model versions, so you can revert without shipping a new build.
  • Shadow or canary deployments when changing the model version behind a deployment.

Modern practice worth adopting

SLOs as code

Keep SLO definitions in version control (for example, the OpenSLO format) and generate alerts and dashboards from them.

Dashboards as code

Provision Grafana dashboards from templates, so every new service gets golden signals automatically.

Game days

Practice failures on purpose: throttle a deployment or fail a region, and see whether alerts and runbooks hold up.

Learning reviews

Go beyond root cause and study how responders actually made sense of the incident. Find what helped, not just what broke.

AI-assisted response

LLMs can summarize timelines and draft queries, but people stay accountable for decisions. Verify anything an AI suggests.

Platform engineering

Give CFTs paved roads (instrumentation libraries, deployment templates) so reliability is the default, not extra work.
