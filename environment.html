Background: Nimbus

Everything in this guide is set in one environment. Read this page first, whatever your role. It explains what Nimbus is, how a request flows through it, who owns each piece, how we measure it, and the tools and processes we have (and don't have yet).

  • Nimbus is a desktop AI companion. The desktop client, the local Agent, and the cloud services are all written in Rust.
  • A device orchestrator decides whether each request is answered on the device by a small local model, or sent to the cloud: Front Door (CDN) → APIM → cloud orchestrator → feature services → Azure AI Foundry.
  • Most incidents involve AI latency, error rates, CDN/edge errors, and 401s. Latency is measured at P50 and P95 only.
  • People: the NOC coordinates incidents but can't take actions yet, SRE is centralized, five feature CFTs own features, and the powerful Cloud Infrastructure CFT owns the shared cloud.
  • We're a new, immature team: under 10% dashboard coverage, few runbooks, weak postmortems, a locked-down Jira, PagerDuty for paging, and CFTs split between Slack and Teams.

What Nimbus Is

Nimbus comes pre-installed on Windows PCs. Users open it with a hotkey or from the taskbar, then ask it to search their files, rewrite text, recap meetings, or fix device settings. The Nimbus app (UI) and the Nimbus Agent (a background service that collects device context) are Rust binaries that update themselves through staged rollouts. A device orchestrator inside the Agent handles simple requests on the device with a small local model (quick rewrites, settings lookups, simple Device Care steps) and sends everything else to the cloud.

Three things make Nimbus harder to run than a typical web service:

  • The client is on the user's machine. Its network, proxy, clock, and version are out of our control. Several client versions are always live at once.
  • The backend is LLM inference. Latency depends on token counts, model capacity, and quota. A healthy model call can still take several seconds.
  • There are many layers between the user and the model. CDN, gateway, auth, and services can each fail in their own way. Knowing which layer returned an error is half the diagnosis.

Architecture

A Request, Step by Step

  1. Device orchestratorThe Agent's orchestrator looks at the request and the device state. Simple tasks are answered by the on-device model in well under a second, with no cloud call at all. Everything else goes to the cloud. If the local model fails, it falls back to the cloud.
  2. Sign-in tokenFor cloud calls, the client uses an Entra ID token and refreshes it before it expires. If the refresh fails, or the device clock is wrong, you get 401s.
  3. Azure Front DoorThe CDN edge terminates TLS, applies WAF rules, and forwards to APIM. Edge problems show up as 502/503/504 or 403 before our code ever runs.
  4. APIM gatewayValidates the token, applies rate limits, and forwards to the cloud orchestrator.
  5. Cloud orchestratorOwned by Cloud Infrastructure. It routes each request to the right feature service and applies cross-feature policies. Every cloud request passes through it, so when it degrades, every feature degrades.
  6. Feature serviceThe CFT's Rust service builds the prompt, calls retrieval and tools, then calls Foundry with a managed identity.
  7. Azure AI FoundryThe model streams tokens back. Over PTU capacity, requests spill to pay-as-you-go or get 429s.
Which layer answered?

The same status code can come from different layers. A 401 could come from APIM (bad client token) or from Foundry (managed identity problem). A 503 could come from Front Door (origin down) or from Foundry (overloaded). Always establish which layer returned the error. The SRE investigate page shows how.

What Rust Means for Incidents

Rust removes whole classes of crashes, such as null pointers and data races, but it has its own failure modes. You'll see these in Nimbus:

ServicesBlocking work on the async runtime (tokio)Latency climbs for every endpoint on the instance while CPU stays moderate. Health checks time out.

Reality Check: Cloud Infrastructure Is Powerful

Cloud Infrastructure owns almost everything every other team depends on, and they control their own change process. Incidents go faster when you bring them evidence rather than accusations, and escalate through management rather than around them. See Working With Cloud Infrastructure.

Gray zones

When a feature's model calls slow down, is it the CFT's prompt or Cloud Infrastructure's capacity? The working rule: the affected CFT owns it until the evidence points to shared infrastructure. Meanwhile the NOC coordinates and SRE investigates, so nobody waits for ownership to be settled before mitigating.

Telemetry Pipeline

The Rust services and client use the tracing and opentelemetry crates and export OTLP to an OpenTelemetry Collector gateway. Rust has no direct Azure Monitor exporter, so the Collector translates the data into Application Insights. Front Door and APIM send diagnostic logs to Log Analytics, which means a different place to query.

How We Measure: P50 and P95

Latency is tracked at two percentiles only:

P50 (Median)

Half of requests are faster than this. This is the typical experience.

P95

95% are faster than this, and 1 in 20 users waits longer. This is the bad-day experience.

Reality check: what P95 doesn't show

P95 hides the worst 5% of requests. For a feature with a million requests a day, that's 50,000 slow experiences P95 can't see. Adding P99 is on the maturity roadmap. Until then, when P95 looks fine but users complain, look at the slowest individual requests directly.

Known Maturity Gaps

Reality check: plan around these
  • Under 10% dashboard coverage. Expect to query rather than glance at a dashboard.
  • Few runbooks. Most incidents will be the first time someone has written down how to handle them.
  • Inconsistent naming. cloud_RoleName may be recap-svc, meeting_recap, or unknown_service.
  • Broken trace propagation from the desktop client. Traces often start at APIM.
  • The Collector is a single point of failure. If it drops data, telemetry looks quiet, not broken.
  • No agreed SLOs. Alerts are raw thresholds.
  • Slow or unclear CFT response. Some CFTs have no on-call, and two aren't on Slack.
