The Nimbus environment

Before you can troubleshoot Nimbus you need a picture of how it works: how a request moves through the system, who owns each piece, and where the telemetry is good, patchy, or missing.

  • Nimbus is a desktop AI companion. A Windows client sends requests through an APIM gateway to per-feature orchestration services, which call Azure AI Foundry.
  • Five CFTs each own one feature experience. A Platform team owns the gateway and Foundry capacity, which every CFT shares.
  • Telemetry flows OpenTelemetry → Application Insights → Grafana. Fewer than 10% of services have a usable dashboard, so be ready to write KQL.
For senior managers · understanding the risk in this setup

What matters to you

  • Every CFT depends on one shared AI backbone. A problem there affects all features at once.
  • Ownership between CFTs and Platform has gray zones, and those gray zones slow incidents down.
  • Less than 10% dashboard coverage means diagnosis depends on a few experts.

Questions to ask

  • Which features matter most to the business, and are they protected from the others?
  • Where do teams share capacity, and who decides priority when it runs out?
  • For each feature, who gets paged? Is that written down?
  • Could we diagnose a problem if our one expert were on vacation?

What Nimbus is

Nimbus ships pre-installed on Windows PCs. Users open it with a hotkey or from the taskbar, then ask it to search their files, rewrite text, recap meetings, or fix device settings. A local Nimbus Agent service gathers device context and handles lightweight tasks on the device. Anything generative goes to the cloud.

Two things make Nimbus harder to run than a typical web service:

  • The client is on the user's machine. You don't control its network, its version, or whether its telemetry arrives. Rollouts are staged over days, so several client versions are always live at once.
  • The backend is LLM inference. Latency depends on token counts, model capacity, and quota, not only on your code. A healthy model call can still take several seconds.

Architecture

A request, step by step

  1. Desktop clientThe user asks something. The Nimbus app collects context through the local Agent and sends an HTTPS request carrying a feature identifier and client version.
  2. APIM gatewayAzure API Management authenticates the device, applies per-feature rate limits, and routes to the right orchestration service.
  3. OrchestrationThe CFT's service builds the prompt. It may first call retrieval or tools (AI Search, Microsoft Graph, device APIs), then calls a Foundry model deployment.
  4. Azure AI FoundryThe model generates a response. Interactive features stream tokens back. PTU deployments have fixed capacity, and requests over that limit spill to pay-as-you-go or get 429s.
  5. Back to the userThe response streams through orchestration and APIM to the client, which renders it. The user feels time to first token most of all.

Gray zones

When a feature's model calls get slow, is that the CFT's problem (their prompt grew) or Platform's (capacity)? The working rule: the CFT whose feature is affected owns the incident until the evidence points to shared infrastructure, and then Platform joins. Nobody waits for ownership to be settled before mitigating.

Telemetry pipeline

Services and the desktop client use OpenTelemetry SDKs with the Azure Monitor exporter. Data lands in one workspace-based Application Insights resource. Grafana reads it through the Azure Monitor data source, so anything you can query in KQL, you can chart in Grafana.

Known maturity gaps

Reality check: plan around these, don't be surprised by them
  • Grafana coverage is under 10%. Most services have no dashboard, and some of the ones that exist chart the wrong thing.
  • Inconsistent naming. cloud_RoleName might be recap-svc, MeetingRecap.Api, or the default unknown_service.
  • Broken trace propagation. The desktop client often doesn't send traceparent, so client and server spans don't join up.
  • Aggressive sampling. Some services sample at 10%, which hides rare failures. Use itemCount when you count things.
  • No agreed SLOs. Alerts are raw thresholds, such as "error count > 50", that don't reflect user impact.
  • Ownership gaps. Some alerts route to channels nobody watches.

The observability maturity page has the plan for fixing these.
