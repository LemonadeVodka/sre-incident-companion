Background: Nimbus

Everything in this guide is set in one environment. Read this page first, whatever your role. It explains what Nimbus is, how a request flows through it, who owns each piece, how we measure it, and the tools and processes we have (and don't have yet).

  • Nimbus is a cross-device AI assistant built into PCs, phones, tablets, and wearables. It's local-first: most requests run on the device's NPU, and only the prompt and minimal context go to the cloud. Client, Agent, and cloud services are written in Rust.
  • Context syncs across a user's devices peer-to-peer on the same network, or through an encrypted sync relay otherwise.
  • A device orchestrator decides whether each request is answered on the device by a small local model, or sent to the cloud: Front Door (CDN) → APIM → cloud orchestrator → feature services → Azure AI Foundry.
  • Most incidents involve AI latency, error rates, CDN/edge errors, and 401s. Latency is measured at P50 and P95 only.
  • Some features depend on third-party partners (meeting platforms, productivity suites, OEM device APIs, partner AI skills) through connectors owned by a Partner Integrations CFT.
  • People: an offshore NOC coordinates incidents but can't take actions yet, SRE is centralized, five feature CFTs own features, and the powerful Cloud Infrastructure CFT owns the shared cloud.
  • We're a new, immature team: under 10% dashboard coverage, few runbooks, weak postmortems, a locked-down Jira, PagerDuty for paging, and CFTs split between Slack and Teams.
Applies Anywhere

Whatever your product, draw this picture first: every hop a request takes, who owns each hop, and where your telemetry is blind. Most incident time is lost working out which layer is failing and who owns it. See Using This Guide Anywhere to map Nimbus terms to your own.

What Nimbus Is

Nimbus ships built into more than 80 PC configurations (16 GB of memory or more), plus phones, tablets, and a smartwatch. Users talk to it by voice ("Hey Nimbus") or chat, in six languages. It works at the system level, keeping context as people move between devices.

Ask Nimbus

Voice and chat questions over the user's personal knowledge base (encrypted, on the device), with an optional research partner for web answers.

Catch Up

Cross-device summaries of notifications, messages, mail, and meetings: "what did I miss?"

Next Step

Anticipates the next task. For example, it opens on your laptop the document you were reading on your phone.

Writing Assist

Rewrite, summarize, and draft in any app.

Device Care

Diagnoses and fixes device problems using tools, drivers, and OEM support APIs.

Live

Real-time multimodal help (voice, screen, camera). Newer and heavier on cloud capacity.

Local-first. A local inference engine on the device's NPU handles most requests. The personal knowledge base is encrypted and stays on the device. When a request needs larger-model reasoning or internet data, Nimbus sends only the prompt and the context that request needs to the cloud. That means many requests never reach our cloud telemetry at all.

Three things make Nimbus harder to run than a typical web service:

  • The client is on the user's machine. Its network, proxy, clock, and version are out of our control. Several client versions are always live at once.
  • The backend is LLM inference. Latency depends on token counts, model capacity, and quota. A healthy model call can still take several seconds.
  • There are many layers between the user and the model. CDN, gateway, auth, and services can each fail in their own way. Knowing which layer returned an error is half the diagnosis.

Architecture

A Request, Step by Step

  1. Device orchestratorThe Agent's orchestrator looks at the request and the device state. Simple tasks are answered by the on-device model in well under a second, with no cloud call at all. Everything else goes to the cloud. If the local model fails, it falls back to the cloud.
  2. Cross-device syncWhen a user moves between devices, context syncs peer-to-peer if they're on the same network, otherwise through the encrypted sync relay. If the relay fails, single-device use still works, but continuity breaks: Next Step and cross-device Catch Up stall.
  3. Sign-in tokenFor cloud calls, the client uses an Entra ID token and refreshes it before it expires. If the refresh fails, or the device clock is wrong, you get 401s.
  4. Azure Front DoorThe CDN edge terminates TLS, applies WAF rules, and forwards to APIM. Edge problems show up as 502/503/504 or 403 before our code ever runs.
  5. APIM gatewayValidates the token, applies rate limits, and forwards to the cloud orchestrator.
  6. Cloud orchestratorOwned by Cloud Infrastructure. It routes each request to the right feature service and applies cross-feature policies. Every cloud request passes through it, so when it degrades, every feature degrades.
  7. Feature serviceThe CFT's Rust service builds the prompt, calls retrieval and tools, then calls Foundry with a managed identity.
  8. Partner integrationsSome features call third-party services through connectors: Catch Up pulls Zoom and Webex transcripts, Ask Nimbus and Writing Assist use Microsoft 365 and Google Workspace context, and Device Care calls OEM warranty and driver APIs. Partners have their own outages, rate limits (429), and OAuth tokens that expire (401).
  9. Azure AI FoundryThe model streams tokens back. Over PTU capacity, requests spill to pay-as-you-go or get 429s.
Which layer answered?

The same status code can come from different layers. A 401 could come from APIM (bad client token) or from Foundry (managed identity problem). A 503 could come from Front Door (origin down) or from Foundry (overloaded). Always establish which layer returned the error. The SRE investigate page shows how.

Sync & Relay

The sync relay is what makes Nimbus feel like one assistant across devices. It's a cloud service, so it can fail like one:

Because synced context is end-to-end encrypted, the relay can't see what it carries. Diagnosis relies on client telemetry and relay health metrics, not content.

Partner Integrations

Most third-party integrations run through an integration-platform partner (an iPaaS). It brokers OAuth and the APIs for mail and calendar (Gmail, Outlook), team chat (Slack), and notes apps. A separate research partner powers web answers in Ask Nimbus. Partners extend what Nimbus can do, but they add dependencies we don't control. When a partner fails, our job is to contain it (disable that connector, degrade gracefully, tell users) and to work the relationship.

The People

Incidents are as much about people as systems. These are the people in our story, written as archetypes so the lessons apply anywhere:

You: Senior Manager, Reliability Operations

You lead a contract NOC, FTE SREs in the US and India, and an Operations lead. You decide, unblock, develop people, manage up, and report to executives. This playbook is written for you.

The Contract NOC

A vendor-run, offshore team that watches 24/7, declares, and coordinates incidents. Many work in a second language, and technical depth is still growing. You manage through the vendor: contract, SLAs, scorecard. They have no production tooling yet, so they request actions from owners.

The SREs (US + India)

Full-time engineers split across two regions, working follow-the-sun. They provide the Technical Lead in incidents, and they're centralized rather than embedded in CFTs. The risk to watch is "toil goes to one region, interesting work to the other".

The Operations Lead

Runs process: rotations, the vendor relationship day to day, reporting. Strong on organization, still growing technically and working on it. One of your highest-leverage people to develop.

The CFTs and Cloud Infrastructure

Feature CFTs, the Client CFT, and the Partner Integrations CFT own the code. Cloud Infrastructure owns the shared cloud and runs its own change process. Evidence moves them, and accusations don't.

Morgan, the Director

Morgan (they/them) is your director: highly technical, impatient, and low on EQ. Morgan dives into the weeds in incidents, questions engineers' competence in public, and can leave the team demotivated, while often being technically right. Managing up to Morgan and shielding the team is covered in A Technical, Low-EQ Leader. Morgan also appears in the tabletop exercises.

What Rust Means for Incidents

Rust removes whole classes of crashes, such as null pointers and data races, but it has its own failure modes. You'll see these in Nimbus:

ServicesBlocking work on the async runtime (tokio)Latency climbs for every endpoint on the instance while CPU stays moderate. Health checks time out.

Reality Check: Cloud Infrastructure Is Powerful

Cloud Infrastructure owns almost everything every other team depends on, and they control their own change process. Incidents go faster when you bring them evidence rather than accusations, and escalate through management rather than around them. See Working With Cloud Infrastructure.

Gray zones

When a feature's model calls slow down, is it the CFT's prompt or Cloud Infrastructure's capacity? The working rule: the affected CFT owns it until the evidence points to shared infrastructure. Meanwhile the NOC coordinates and SRE investigates, so nobody waits for ownership to be settled before mitigating.

Telemetry Pipeline

The Rust services and client use the tracing and opentelemetry crates and export OTLP to an OpenTelemetry Collector gateway. Rust has no direct Azure Monitor exporter, so the Collector translates the data into Application Insights. Front Door and APIM send diagnostic logs to Log Analytics, which means a different place to query.

How We Measure: P50 and P95

Latency is tracked at two percentiles only:

P50 (Median)

Half of requests are faster than this. This is the typical experience.

P95

95% are faster than this, and 1 in 20 users waits longer. This is the bad-day experience.

Reality check: what P95 doesn't show

P95 hides the worst 5% of requests. For a feature with a million requests a day, that's 50,000 slow experiences P95 can't see. Adding P99 is on the maturity roadmap. Until then, when P95 looks fine but users complain, look at the slowest individual requests directly.

Known Maturity Gaps

Reality check: plan around these
  • Under 10% dashboard coverage. Expect to query rather than glance at a dashboard.
  • Few runbooks. Most incidents will be the first time someone has written down how to handle them.
  • Inconsistent naming. cloud_RoleName may be recap-svc, meeting_recap, or unknown_service.
  • Broken trace propagation from the desktop client. Traces often start at APIM.
  • The Collector is a single point of failure. If it drops data, telemetry looks quiet, not broken.
  • No agreed SLOs. Alerts are raw thresholds.
  • Slow or unclear CFT response. Some CFTs have no on-call, and two aren't on Slack.
