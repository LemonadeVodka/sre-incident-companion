Beginner troubleshooting

You've just been paged and you're not sure where to start. This page takes you through the first 30 minutes, step by step. You don't have to solve the problem. You have to confirm it, scope it, communicate it, and get the right people involved.

  • Six steps: confirm, scope, check outside causes, find the dominant error, check latency, escalate.
  • Use the App Insights Failures and Performance views first. They work even when there's no dashboard.
  • A good escalation names the feature, the impact, when it started, and what you've already checked.
You're allowed to escalate early

Nobody expects a first responder to diagnose a Foundry capacity problem. Paging the owning CFT after 10 minutes with good notes is a success. Spending an hour alone is the real failure mode.

For senior managers · supporting your first responders

Your role

  • Make it safe to escalate early. A false alarm is better than a silent hour.
  • Make sure new on-call engineers shadow someone experienced before they're primary.
  • Check that the on-call engineer knows who to page for each feature.

Questions to ask the on-call engineer

  • Is it confirmed real, or still possibly a noisy alert?
  • Which feature, and roughly how many users?
  • Have you escalated? To whom?
  • Is anyone helping you right now?

Avoid

  • Criticizing someone for paging "too early".
  • Expecting a first responder to find the root cause.

Step 1: Confirm it's real

Alerts can be noisy, especially the raw-threshold ones we still have. Before you mobilize anyone, check that users are actually affected.

  1. Read the alert.Which service (cloud_RoleName), which metric, which threshold, which time window?
  2. Open Application Insights → Failures for the last hour. Is the failed-request line actually elevated?
  3. Compare with yesterday.Is this normal for this time of day? Proactive Tips, for example, is bursty every morning.
  4. Check volume.If requests dropped to zero, the error rate can look perfect while everything is broken.
KQLStarter: error rate for the last hour, 5-minute bucketsIs the error rate really up?
requests
| where timestamp > ago(1h)
| summarize total = sum(itemCount), failed = sumif(itemCount, success == false) by bin(timestamp, 5m)
| extend error_pct = round(100.0 * failed / total, 2)
| render timechart

Step 2: Scope it

Scope tells you severity and who owns the problem. Answer these four questions:

QuestionHow to answerWhy it matters
Which feature experiences?Error rate by featureOne feature points to that CFT. All features point to Platform.
Which region?Group by client_CountryOrRegion, or check the Foundry target hostA regional problem can often be handled by failing over.
Which client versions?By client versionIf only the new build is affected, halt the rollout.
Which Foundry deployment?Model latency by deploymentA shared deployment means other features may be hit next.

Step 3: Check the outside world

  • Azure status page and Service Health in the Azure portal for Azure OpenAI / AI Foundry, API Management, and AI Search in our regions.
  • Resource health of the Foundry resource and the APIM instance.
  • Recent changes: deploys, feature flags, prompt template changes. Check the team channels and run version first seen.
  • Client rollout status: is a new desktop build ramping up right now?
  • Other incidents: is another CFT already working on this? Join their channel rather than opening a second one.

Step 4: Find the dominant error

In Application Insights → Failures:

  1. Pick the Operations tab.Sort by failed count to see which operation (API route) fails most.
  2. Check the Dependencies tab.Are the failures coming from a dependency, such as the Foundry host or AI Search? That usually explains the operation failures.
  3. Check the Exceptions tab.Find the top exception type and click into a sample.
  4. Read the result codes.Use the cheat sheet below.
CodeUsually meansUsually owned by
429Throttled: quota or rate limit hitPlatform (quota), plus the CFT if its traffic is the cause
500 from our serviceA bug or unhandled dependency failure in our codeOwning CFT
500/502/503 on the Foundry dependencyModel service troublePlatform, possibly Azure
504 / 408 / TaskCanceledTimeout. Something upstream is too slow.Treat it as latency (Step 5)
400 on the Foundry dependencyBad request, or the prompt was blocked by the content filterOwning CFT
401/403Auth problem: expired key, managed identity, or APIM policyPlatform or CFT, depending on the layer

Step 5: Check latency

In Application Insights → Performance:

  • Switch the chart to the 95th or 99th percentile. Averages hide the pain.
  • Select the slow operation and look at the dependency breakdown on the right. Is the Foundry call the long bar?
  • Click Samples and open a slow one to see the end-to-end transaction.
KQLStarter: P95 latency by serviceWhich service got slow?
requests
| where timestamp > ago(1h)
| summarize p95_ms = percentile(duration, 95), requests = sum(itemCount) by cloud_RoleName
| order by p95_ms desc
Reality check: names are messy

You might see recap-svc, MeetingRecap.Api, and unknown_service all at once. The ownership table and the service inventory query help you work out which is which.

Step 6: Escalate well

Page the owner from the ownership table. A good page saves the next person 15 minutes:

TextEscalation messagePaste into the page or the incident channel
Paging [CFT / Platform] for Nimbus [feature].
Impact: [e.g. Device Care error rate 12% (baseline <1%) for ~20 min]
Scope: [features / regions / client versions / deployment]
Dominant error: [e.g. 429 on chat-small]
Checked: Azure status (green), no deploys in last 2h, [query links]
Severity proposed: Sev [X]. Channel: [link]

Your tools at a glance

Failures

Failed operations, dependencies, and exceptions, all with drill-down. Start here for errors.

Performance

Operation durations by percentile, with a dependency breakdown. Start here for latency.

Transaction search

Find a single request by operation ID and see its end-to-end trace.

Live metrics

A near-real-time view of request rate and failures. Use it to confirm a mitigation worked.

Logs (KQL)

Everything else. Use the query library.

Grafana

Only a few services have dashboards. Use them if they exist, but don't trust them blindly.

Common beginner mistakes

  • Trusting averages. Always look at P95 and P99.
  • Counting rows instead of requests. Use sum(itemCount) because of sampling.
  • Assuming green dashboards mean healthy. No data looks green too. Check volume.
  • Debugging alone for an hour. Escalate with notes after 15 minutes if you're stuck.
  • Forgetting the timeline. Write down timestamps as you go, because you won't remember them later.

Scenario: Device Care alert "failed requests > 100 in 5 min"

Failures shows Device Care failing at 9% (baseline 0.6%). The Dependencies tab shows 429 on chat-small. No deploys today. Azure status is green. What do you do?

  1. This is real and it's an interactive feature: propose Sev 2.
  2. Since 429s on a shared deployment point to Platform, page Platform and the Device CFT.
  3. Mention that Proactive Tips shares chat-small, and suggest running token consumption by caller.
  4. Post the initial update and start the timeline.
