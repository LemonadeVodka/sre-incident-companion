Intermediate troubleshooting

You can confirm and scope an incident. Now find where the problem is. Split latency into hops, follow individual traces, read error types correctly, and tie the problem to the change that caused it.

  • Every request has a latency budget across its hops. Find the hop that went over.
  • TTFT up points to queueing or capacity. Total up with TTFT flat points to longer outputs.
  • 429s, 5xx, and timeouts have different owners and fixes. Don't lump them together as "errors".
  • Most incidents follow a change. Check application_Version, flags, prompts, and model version auto-upgrades.
For senior managers · when the team is narrowing it down

Your role

  • Get the right team onto the call when the evidence points to another CFT or to Platform.
  • Approve rollbacks, even if that delays a feature launch.
  • Settle "whose problem is it?" arguments quickly. Mitigation comes first.

Questions to ask

  • Where is the time going: our code, a data lookup, or the AI model?
  • Did anything change in the last 24 hours (a release, a prompt, a model version)?
  • Is this one team's problem or the shared platform's?
  • Can we roll back, and what's the risk if we do?

Avoid

  • Waiting for ownership to be settled before allowing a mitigation.

Decomposing latency hop by hop

Each hop in the request path uses part of the user's patience. Here is an illustrative P95 budget for Writing Assist. Learn the shape so you can spot which segment grew.

  1. Get the per-hop breakdown.Run Dependency breakdown for the affected service, now and for yesterday's baseline.
  2. Find the hop that grew.Compare against yesterday, not against an ideal. A hop going from 600 ms to 2.4 s stands out.
  3. Check the residual.If the request time is much bigger than the sum of its hops, the time is in our own code or in calls nobody instrumented.
  4. Go one level deeper.For the model hop, split TTFT from generation. For retrieval, split it by target.

Following a trace

Aggregates tell you that something is slow. One trace tells you why.

  1. Find candidates.Run slowest operations to get a handful of operation_Ids.
  2. Open the end-to-end view.In Transaction search, paste an ID to see the Gantt chart. Or run trace walk in KQL.
  3. Read the Gantt chart.Look for long bars (a slow hop), gaps between bars (time in our own code), repeated bars (retries), and bars in sequence that could run in parallel.
  4. Compare with a fast trace for the same operation. The difference is your lead.
Reality check: broken traces

Many desktop clients don't send traceparent, so traces start at APIM. Some services also start a new trace when they make async calls. If a trace looks too short, it probably is cut short. Join on a business ID (request ID or session ID in customDimensions) if one is logged.

429s cascade

A service that retries 429s straight away, without backoff, multiplies its own traffic and makes throttling worse for everyone. If calls per operation are rising together with 429s, you're watching a retry storm. See Advanced.

Timeout budgets

Timeouts should get shorter as you go deeper into the stack, so the layer closest to the user gets to decide what happens. If the client gives up at 20 s but the service keeps waiting 60 s for the model, the server does 40 s of work nobody will see, while holding a connection and quota.

LayerInteractive (Writing Assist)Background (Proactive Tips)
Desktop client30 s (with streaming progress)n/a
APIM28 s120 s
Orchestration → model25 s, at most 1 retry with backoff90 s, retry with exponential backoff
Orchestration → retrieval2 s, then answer without retrieval10 s

Better still is deadline propagation: pass the time remaining down the stack, so each layer knows how long it has left.

Correlating with change

Before you go deep, ask "what changed?" The usual suspects in Nimbus:

  • Service deploys: errors by application_Version and version first seen.
  • Desktop client rollouts: by client version.
  • Prompt template or feature flag changes: these often aren't in telemetry at all. Ask the CFT, and check their config repo history.
  • Model version changes: Foundry deployments set to auto-update can move to a new model version. The new version may differ in latency, output length, or content-filter behavior.
  • Quota or PTU changes: capacity reassigned between deployments.
  • Traffic changes: a marketing push, a new market, Monday morning.

Building an ad-hoc Grafana panel

Is there no dashboard for the service you're investigating? Build a throwaway one in 3 minutes, so the whole incident channel looks at the same chart.

  1. New dashboard → Add visualization, then choose the Azure Monitor data source.
  2. Service: Logs, then select the Nimbus Application Insights resource.
  3. Paste a query from the library, replacing ago(...) with $__timeFilter(timestamp) and the bin size with $__interval.
  4. Format as Time series, set the unit to milliseconds or percent, and add a threshold line at the baseline.
  5. Share the link in the incident channel. Afterwards, save it to the "Incident scratch" folder and file a follow-up to make it a real dashboard.

Percentiles and sampling gotchas

  • Percentiles don't average. The average of five services' P95s isn't the overall P95. Recompute from raw data.
  • Low volume makes P99 noisy. At 50 requests per bucket, P99 is a single request. Widen the bins.
  • Sampling hides rare events. At 10% sampling, a 0.1% error might not show up at all. See sampling bias.
  • Mixing successes and failures skews latency. Fast failures make P95 look better during an outage.

Practice

Scenario: Smart Search P95 went from 3.5 s to 9 s at 14:10

The dependency breakdown shows the model hop is unchanged, retrieval P95 went from 0.5 s to 5.8 s, and AI Search is returning some 503s. No Nimbus deploys. What next?

Show suggested answer
  1. Since retrieval is the hop that grew, focus on AI Search, not on Foundry.
  2. Check AI Search metrics (throttled queries, latency, replica count) and its resource health. Is the shared index owned by Platform?
  3. Check whether Smart Search's query volume or fan-out grew, by comparing calls per operation to retrieval.
  4. Mitigate: lower the retrieval timeout and degrade gracefully, scale AI Search replicas, or reduce fan-out.
