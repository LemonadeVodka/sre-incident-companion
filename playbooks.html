Playbooks

Runbooks for the incidents we see most. Every playbook has the same shape, so you always know where to look: Symptoms → Check first → Likely causes → Mitigate → Escalate → Verify.

  • Not sure which playbook fits? Use the triage tool.
  • Playbooks guide you. They don't replace judgment. If the evidence doesn't fit, say so and switch.
  • The print view is tidy if you want these on paper.
For senior managers · how to use the playbooks

Your role

  • Make sure every recurring incident type gets a playbook.

Questions to ask

  • Which playbook are we following? Does the evidence fit it?
  • Which incidents do we keep having that don't have a playbook yet?

Latency spike on one feature experience

Usually Sev 2–3Owner: feature CFTIntermediate
Symptoms
  • P95 for one feature (say, Writing Assist) is well above baseline. Other features look normal.
  • Users report "Nimbus is slow" for one action.
Check first
  1. Latency by feature, now vs yesterday: confirm only one feature is affected.
  2. Dependency breakdown: which hop grew?
  3. By service version: did a deploy line up with the start?
  4. Token growth: did prompts get bigger?
Likely causes
  • A service deploy, or a prompt template change that added context.
  • The feature's dedicated deployment is saturated.
  • A retrieval dependency (AI Search, Graph) slowed down.
  • A new code path doing synchronous work.
Mitigate
  • Roll back the deploy or flip the prompt flag back.
  • Tighten the retrieval timeout and answer without retrieval.
  • Lower max_tokens or switch to the small model temporarily, if quality allows.
Escalate
The feature CFT's on-call owns this. Bring in Platform if the model hop grew and the deployment is shared.
Verify
P95 back within 20% of baseline for 30 minutes, and the error rate unchanged.
Manager lens
  • Ask: "Did something change recently, and can we roll it back?" and "How many users of this feature are affected?"
  • Decide: approve a rollback even if it delays this CFT's launch or experiment.
  • After: ask how the change got through without anyone noticing the latency cost.

429 throttling surge

Sev 2 if interactiveOwner: Platform + noisy CFTAdvanced patterns
Symptoms
  • Spike in 429 on Foundry dependencies.
  • Users see "Nimbus is busy, try again." Latency also rises because of retries.
Check first
  1. 429 by deployment and caller: which deployment, and who is throttled?
  2. Token consumption by caller: who is using the quota?
  3. Retry detector: is it a retry storm?
  4. Azure Monitor: the deployment's PTU utilization and its tokens-per-minute limit.
Likely causes
  • A background workload burst (Proactive Tips batch) on a shared deployment.
  • An organic traffic peak (Monday 09:00) above capacity.
  • Prompt growth using up tokens-per-minute faster.
  • Retries without backoff multiplying the load.
  • Quota reassigned or reduced.
Mitigate
  • Pause or rate-limit background callers (feature flag or APIM policy).
  • Turn on or widen spillover from PTU to pay-as-you-go.
  • Temporarily route the interactive feature to a different deployment.
  • Make sure clients honor retry-after, and reduce retry counts.
Escalate
Platform owns quota and routing. Bring in the CFT generating the load to pause it. Request a quota increase if the demand is real.
Verify
Throttle rate under 1% for interactive callers for 30 minutes. Calls per operation back to baseline.
Manager lens
  • Ask: "Whose traffic is using up the capacity, and can it pause?" and "Is this real demand, or are we retrying ourselves into the ground?"
  • Decide: which feature gets priority (usually customer-facing over background), and whether to approve extra spend on overflow capacity.
  • After: ask who decides capacity priority between CFTs. If the answer is "nobody", that's the real fix.

Foundry 5xx / platform degradation

Sev 1–2Owner: PlatformIntermediate
Symptoms
  • 500/502/503 on Foundry dependencies across several features.
  • Model latency up across deployments, sometimes in one region only.
Check first
  1. Model latency and failures by deployment, grouped by target, which gives you the region.
  2. Azure status page, Service Health, and the Foundry resource health.
  3. Is anything else on our side changing, such as APIM policies or network config?
Likely causes
  • An Azure platform incident in the region.
  • A model version rollout issue on the provider side.
  • Network or private endpoint problems between our services and Foundry.
Mitigate
  • Fail over to Sweden Central (see the failover checklist).
  • Shed non-interactive load to protect interactive features.
  • Make the client fail fast with a friendly message instead of hanging.
Escalate
Declare Sev 1 if most users are affected. Platform is IC. Open an Azure support case at the highest severity early, because you can always lower it.
Verify
Error rate back to baseline in the primary region (if failing back) or stable on the secondary. Track failback as its own change.
Manager lens
  • Ask: "Is this on Microsoft's side? Is a support case open, and at what severity?" and "Can we move traffic to the other region?"
  • Decide: approve the failover (check data residency and cost), notify executives, and approve customer or status-page messaging.
  • After: ask what we can do to limit the impact next time, even if the provider caused it.

Slow first token

Sev 2–3Owner: feature CFT → PlatformIntermediate
Symptoms
  • Streaming features (Writing Assist, Device Care) feel slow to start. The spinner stays up longer.
  • Total duration may look normal.
Check first
  1. TTFT vs total duration: is TTFT really up?
  2. Input token growth: bigger prompts mean slower prefill.
  3. PTU utilization: is traffic queueing or spilling to pay-as-you-go?
  4. Is streaming still on? A config change that disables streaming makes TTFT equal total time.
Likely causes
  • PTU saturation causing queueing.
  • Prompt or context growth.
  • Retrieval added before the model call (sequential, not parallel).
  • Streaming disabled or buffered by a proxy or APIM policy.
Mitigate
  • Shed background load from the shared deployment.
  • Trim context, or revert the prompt change.
  • Turn streaming back on, or remove response buffering in APIM.
Escalate
The CFT owns prompt and streaming issues. Platform owns PTU saturation.
Verify
TTFT P95 back under 1.5 s (Writing Assist) for 30 minutes.
Manager lens
  • Ask: "Is it a capacity problem or something in how we build the request?" and "How noticeable is it to users?"
  • Decide: whether to accept slightly lower answer quality (smaller model, less context) for a faster experience while the team fixes it.
  • After: ask whether "time until the user sees something" is tracked as a target for every customer-facing feature.

Errors after a desktop client rollout

Sev 2 while rampingOwner: Client CFTBeginner-friendly
Symptoms
  • Error rate or latency up, concentrated in the newest client.version.
  • Crash reports or support tickets mentioning the new build.
Check first
  1. By client version: compare the new build with the previous one.
  2. Rollout percentage and how fast it's ramping.
  3. What changed in the build: API version, request shape, retry policy, region pinning, telemetry config.
Likely causes
  • The new build calls a changed or unsupported API route.
  • A more aggressive retry or timeout configuration.
  • Larger payloads (more context collected by the Agent).
  • An auth or token-refresh bug.
Mitigate
  • Halt the rollout immediately. This is cheap and reversible.
  • Use a server-side feature flag to turn off the new code path for that version.
  • If possible, adapt on the server (accept the old and new request shapes).
Escalate
Client CFT and the release manager. Bring in the CFT whose feature is affected.
Verify
The new version's error rate matches the previous version's. The rollout resumes only after a fix is confirmed.
Manager lens
  • Ask: "Has the rollout been halted?" (this should be the first answer) and "What share of users have the new version?"
  • Decide: hold the release, and coordinate with release management, partners, and support on messaging.
  • After: ask why the staged rollout didn't stop itself automatically.

Dashboards green, users complaining

Sev 3 until measuredOwner: whoever's on call → PlatformAdvanced
Symptoms
  • Support tickets, social posts, or internal reports say Nimbus is broken.
  • The dashboards you have look normal, or there are no dashboards.
Check first
  1. Telemetry volume: did data drop? Missing data looks green.
  2. Request volume vs the usual: fewer requests can mean clients can't connect at all.
  3. By client version and by region: is it a small cohort?
  4. Get 3–5 concrete reports (time, feature, device, version) and look for their traces.
Likely causes
  • Client-side failures (can't reach APIM, auth, crash) that never reach the server.
  • The telemetry exporter is broken, or sampling changed.
  • The feature has no instrumentation, or the dashboard charts the wrong thing.
  • A quality problem: responses succeed but they're wrong or empty.
Mitigate
That depends on what you find. The key step is to get a measurement: build an ad-hoc panel that shows user impact.
Escalate
Platform (Observability) if the telemetry is broken. Client CFT if the failures are client-side.
Verify
You have a metric that shows the problem and its recovery. Add it to a dashboard and an alert as a follow-up.
Manager lens
  • Ask: "How do we know how many users are affected?" If nobody can answer, that's the core finding.
  • Decide: treat "customers told us before our monitoring did" as a serious issue, not bad luck.
  • After: fund the monitoring gap as a top-priority action item, and track it in the maturity roadmap.
