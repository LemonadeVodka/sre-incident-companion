Starter playbooks

We're a new team without many runbooks yet. These eight starter playbooks cover the incidents we expect most. They aren't battle-tested: improve them after every incident, and copy one as the starting point for a new runbook.

  • Every playbook has the same shape: Symptoms → Check first → Likely causes → Verify, then NOC does → SRE does → Manager lens.
  • Not sure which applies? Use the triage tool. No match? Follow the no-runbook method and write a new one afterwards.
  • Managers: the same scenarios are in plain English in Scenarios.
Make them yours

After each incident, update the playbook you used: what was missing, what was wrong, what worked. Use the runbook template for incidents that didn't fit any playbook.

Latency spike on one feature

Usually Sev 2–3Owner: Feature CFTStarter · improve after use
Symptoms
  • P50 and/or P95 for one feature (say, Writing Assist) well above baseline. Other features normal.
  • Users report that one action is slow.
Check first
  1. Latency by feature, now vs yesterday: confirm only one feature is affected.
  2. P50/P95 per hop: model, retrieval, or our own code?
  3. Errors by service version: did a deploy line up with the start?
  4. Token growth: did prompts get bigger?
Likely causes
  • A service deploy, or a prompt template change that added context.
  • A Rust service stalling (async runtime starvation, pool exhaustion). Check by instance.
  • A retrieval dependency (AI Search, Graph) slowed down.
  • The feature's deployment is saturated.
Verify
P50 and P95 back within 20% of baseline for 30 minutes.
NOC does
Run sweep queries 1–2, open the channel, and page the CFT plus SRE if it's Sev 2. If one instance is clearly stalled, restart that instance.
SRE does
Split latency by hop and by instance. Roll back the deploy or prompt flag if it lines up. Tighten the retrieval timeout and degrade gracefully.
Manager lens
Ask: "Did something change, and can we roll it back?" Decide: approve the rollback even if it delays a launch.

429 throttling surge

Sev 2 if interactiveOwner: Platform + noisy CFTStarter · improve after use
Symptoms
  • Spike in 429 on Foundry dependencies.
  • "Nimbus is busy, try again." Latency also rises because of retries.
Check first
  1. 429 by deployment and caller
  2. Token consumption by caller: who is using the quota?
  3. Retry detector: is it a retry storm?
  4. Azure Monitor: the deployment's PTU utilization and its tokens-per-minute limit.
Likely causes
  • A background burst (Proactive Tips batch) on a shared deployment.
  • An organic peak above capacity.
  • Prompt growth.
  • Retries without backoff, or unbounded concurrency in a Rust service.
Verify
Throttle rate under 1% for interactive callers for 30 minutes.
NOC does
Run sweep query 5 and page Platform plus SRE. If Proactive Tips is running and Device Care is affected, pause the batch. Don't scale out.
SRE does
Prove who the noisy neighbor is, then shed background load, enable spillover with Platform, and check retry and concurrency settings.
Manager lens
Ask: "Whose traffic, can it pause, and what does overflow cost?" Decide: which feature gets priority, and whether to approve the overflow spend.

Foundry 5xx / platform degradation

Sev 1–2Owner: PlatformStarter · improve after use
Symptoms
  • 500/502/503 on Foundry dependencies across features.
  • Model latency up across deployments, sometimes in one region.
Check first
  1. Model latency and failures by deployment, grouped by target (region).
  2. Azure status, Service Health, Foundry resource health.
  3. Errors by layer: confirm it's the model layer, not ours.
Likely causes
  • An Azure platform incident in the region.
  • A provider-side model version problem.
  • Network or private endpoint problems.
Verify
Error rate back to baseline. Track failback as its own change.
NOC does
Page Platform plus SRE at high urgency. Turn on the in-app banner if Sev 1–2 is declared.
SRE does
Confirm scope by region and deployment. Coordinate failover with Platform. Open an Azure support case early. Shed background load.
Manager lens
Ask: "Is it Microsoft's side, is a case open, can we fail over?" Decide: approve failover (data residency, cost), executive notice, and customer messaging.

Slow first token

Sev 2–3Owner: Feature CFT → PlatformStarter · improve after use
Symptoms
  • Streaming features feel slow to start, even when total time looks normal.
Check first
  1. Time to first token vs total
  2. Input token growth
  3. PTU utilization: is traffic queueing or spilling to pay-as-you-go?
  4. Is streaming still on? A config change or APIM buffering can turn it off.
Likely causes
  • PTU saturation and queueing.
  • Prompt or context growth.
  • Retrieval added before the model call.
  • Streaming disabled or buffered.
Verify
Writing Assist first-token P95 back under 1.5 s for 30 minutes.
NOC does
Page the feature CFT, and SRE if it's broad. Note whether other features on the same deployment are affected.
SRE does
Separate capacity from prompt-size causes. Shed background load, trim context or revert the prompt, and restore streaming.
Manager lens
Ask: "Capacity or how we build the request?" Decide: accept a temporary quality trade-off (smaller model, less context) for speed.

Errors after a desktop client rollout

Sev 2 while rampingOwner: Client CFTStarter · improve after use
Symptoms
  • Errors, 401s, or crashes concentrated in the newest client version.
  • Support tickets saying "since the update".
Check first
  1. By client version: compare the new build with the previous one.
  2. The rollout percentage and how fast it's ramping.
  3. What changed in the build: API version, retry or timeout config, token refresh, telemetry.
Likely causes
  • A new build calls a changed API.
  • Aggressive retries.
  • A token refresh bug, which shows up as 401s about an hour in.
  • A Rust panic on an unexpected response.
Verify
The new version's error rate matches the previous version's.
NOC does
Halt the rollout straight away, then page the Client CFT plus SRE.
SRE does
Confirm it's the cohort. Use a server-side flag to disable the new code path if one exists. Make sure the rollout stays paused until a fix is verified.
Manager lens
Ask: "Has the rollout been halted? What share of users have the new version?" Decide: hold the release, and coordinate messaging.

Dashboards green, users complaining

Sev 3 until measuredOwner: SRE → PlatformStarter · improve after use
Symptoms
  • Support tickets or social posts say Nimbus is broken. Signals look normal, or quiet.
Check first
  1. Telemetry volume: did data drop? Is the OTel Collector healthy?
  2. Edge errors: a failure before our code runs won't show in App Insights.
  3. By client version and by region.
  4. Get 3–5 concrete user reports (time, feature, version) and look for their traces.
Likely causes
  • Client-side failures (TLS, proxy, clock, crash).
  • The Collector dropping data.
  • A feature with no instrumentation.
  • Quality problems: responses succeed but are wrong.
Verify
You have a metric that shows the problem and its recovery. Add it to a dashboard as a follow-up.
NOC does
Take user reports seriously. Open a channel, page SRE, and collect concrete examples.
SRE does
Get a measurement first (an ad-hoc Grafana panel), then follow the evidence. File the monitoring gap.
Manager lens
Ask: "How do we know how many users are affected?" Decide: treat "customers told us first" as a serious finding, and fund the monitoring fix.

CDN / Front Door errors

Often Sev 1–2 (broad)Owner: PlatformStarter · improve after use
Symptoms
  • 502/503/504 at the edge, often across every feature at once.
  • Or 403s for a group of users (WAF).
  • App Insights may look quiet, because requests never reach our services.
Check first
  1. Edge status codes over time.
  2. Edge errors by error info and route: OriginConnectionError, OriginTimeout, health probes?
  3. WAF blocks by rule if you're seeing 403s.
  4. Who changed what: Front Door, WAF, DNS, certificates.
  5. Azure status for Front Door. Is it one POP or region?
Likely causes
  • APIM unreachable or unhealthy (origin connection, private link, DNS).
  • Origin too slow, so timeouts. Often model latency underneath.
  • Health probes failing, so every origin is marked down.
  • A new or changed WAF rule blocking real traffic.
  • An expired or misconfigured origin certificate.
  • An Azure edge incident.
Verify
Edge 5xx under 0.1% and 403s back to baseline for 30 minutes.
NOC does
Run sweep query 3 and page Platform plus SRE at high urgency. Purging the cache and changing WAF rules are not pre-approved.
SRE does
Use the layer query to separate edge from origin. Work with Platform on origin health, reverting the WAF rule, or rerouting. Communicate early, because impact is usually broad.
Manager lens
Ask: "All users or some regions? Did anyone change a CDN or firewall setting?" Decide: approve the WAF rollback (with security sign-off) and customer messaging.

401 surge

Sev 1–2 if widespreadOwner: Platform / Client CFTStarter · improve after use
Symptoms
  • 401s rising at APIM, or on our services' calls to Foundry.
  • "Please sign in again" loops, or features refusing to work.
Check first
  1. 401s at the gateway by API: every API, or one?
  2. 401s by client version: one build, or everyone?
  3. 401/403 from our services to dependencies: managed identity?
  4. Token validation errors: expired, not yet valid (clock skew), or wrong audience?
  5. Who changed what: APIM policies, app registrations, secrets, role assignments.
Likely causes
  • APIM validate-jwt policy change (audience, issuer).
  • Entra ID incident or signing key rollover.
  • An expired client secret or certificate.
  • A token refresh bug in a new client build.
  • A managed identity role assignment removed (401 or 403 to Foundry).
  • Device clock skew (a small, scattered cohort).
Verify
401 rate back under 0.3% at APIM, and no auth failures on dependencies, for 30 minutes.
NOC does
Run sweep query 4. One client version: halt the rollout and page the Client CFT plus SRE. All versions: page Platform plus SRE. Rotating secrets and changing policies are not pre-approved.
SRE does
Find the rejecting layer, then the cohort, then the change. Revert the policy or config, or renew the secret with Platform. Watch for a token refresh stampede during recovery.
Manager lens
Ask: "Everyone or one app version? What changed in sign-in, keys, or certificates?" Decide: approve emergency sign-in changes, and ask for a secret-expiry calendar afterwards.
