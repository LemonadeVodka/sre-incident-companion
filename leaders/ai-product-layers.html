Know the Layers

Every request to an AI product passes through several layers, and each one can make it slow or make it fail. If you can say which layer a problem is in, you know who owns it, which questions to ask, and how to explain it to executives. This is the most useful mental model you can have.

  • An AI product has ten layers to think about, from the user's device to the model provider, plus the telemetry that lets us see them.
  • Each layer has a typical latency signature and a typical error signature. Learn to recognize them.
  • Each layer has an owner. Locating the layer is half the incident.

Why AI Products Are Different

Slow Is Normal

A healthy model call can take seconds. You have to know each feature's normal P50 and P95, or every number looks alarming.

Capacity Is Shared and Rationed

Model capacity is measured in tokens per minute and shared across teams. One team's batch job can throttle another team's customers.

Two Places to Answer

On-device and cloud. When the device path fails, the cloud quietly absorbs the load until it can't.

Dependencies You Don't Control

The model provider and partners can change, slow down, or fail, and your fix is to contain the damage.

Quality Is a Failure Mode

A fast, successful, wrong answer is still an incident. Watch user feedback as well as error rates.

Changes Hide Everywhere

Prompts, model versions, routing policies, and content filters are all changes, even when no code shipped.

Layer by Layer

For each layer: what it does, who owns it, and how latency and errors show up. The questions to ask are in the Question Builder.

Layer 01

Device & On-Device Model

The app on the user's machine, and a small local AI model that answers simple requests without the cloud.

Owner

Client team (Nimbus: Client CFT)

Latency Looks Like

Quick tasks slow on some devices. Slow app startup. The local model is slow on older hardware or a new driver.

Errors Look Like

Crashes, local model failures, TLS/proxy failures that never reach the server, clock skew causing 401s.

Layer 02

Device Orchestrator (Local vs Cloud)

Decides whether each request is answered on the device or sent to the cloud. If local fails, it falls back to the cloud.

Owner

Client team (Nimbus: Client CFT)

Latency Looks Like

Cloud traffic and latency rise with no server change, because local answers are falling back to the cloud.

Errors Look Like

Routing misconfiguration sends requests to the wrong place. A fallback surge triggers cloud 429s.

Layer 03

Sync & Relay (Cross-Device)

Keeps context in step across a user's devices: peer-to-peer on the same network, or through an encrypted cloud relay.

Owner

Client team + platform team (Nimbus: Client CFT, hosted by Cloud Infrastructure)

Latency Looks Like

Cross-device features (Next Step, cross-device Catch Up) lag. Context shows up late on the second device.

Errors Look Like

Pairing or key-exchange failures, relay 5xx, "can't connect your devices".

Layer 04

Edge / CDN / WAF

The internet-facing entrance: TLS, caching, and the firewall (WAF) in front of everything.

Owner

Platform team (Nimbus: Cloud Infrastructure)

Latency Looks Like

Slow everywhere at once. Origin timeouts (504).

Errors Look Like

502/503/504 at the edge, 403 from WAF rules. Our services may look quiet.

Layer 05

Gateway & Auth

Checks credentials, applies rate limits, and routes requests.

Owner

Platform team (Nimbus: Cloud Infrastructure)

Latency Looks Like

Added time in the gateway itself (policies, token validation).

Errors Look Like

401s (token rejected), 429s (rate limits), auth config changes, signing key rollover.

Layer 06

Cloud Orchestrator

The shared router that sends each cloud request to the right feature service.

Owner

Platform team (Nimbus: Cloud Infrastructure)

Latency Looks Like

Every feature slows together while models and services look normal inside.

Errors Look Like

Errors across all features at once.

Layer 07

Feature Services & Retrieval

Each team's code: builds the prompt, retrieves context, calls the model.

Owner

Feature teams (Nimbus: feature CFTs)

Latency Looks Like

One feature slow. Retrieval slow. Bigger prompts. A stalled instance (Rust runtime).

Errors Look Like

5xx or panics in one feature, failing dependencies.

Layer 08

Integration Platform & Partners

Third-party connectors, mostly through an integration-platform partner (iPaaS): mail, calendar, chat, notes. Also a research partner, meeting platforms, and OEM device APIs.

Owner

Integrations team (Nimbus: Partner Integrations CFT) + the iPaaS vendor

Latency Looks Like

One feature slow only for users of one partner. Partner API slow. Webhooks delayed.

Errors Look Like

Partner 5xx, partner rate limits (429), expired OAuth tokens or consent (401), API/schema changes.

Layer 09

Model Provider (Capacity & Quota)

The AI model service: reserved capacity (PTU), overflow capacity, quotas, model versions.

Owner

Platform team (Nimbus: Cloud Infrastructure, with Azure)

Latency Looks Like

Slow first token (queueing), longer outputs, region problems, capacity saturation.

Errors Look Like

429 throttling (noisy neighbor, retry storms), provider 5xx, content-filter blocks.

Layer 10

Telemetry & Visibility

The data we use to see all of the above: SDKs, collector, App Insights, logs, dashboards.

Owner

Platform team (Nimbus: Cloud Infrastructure Observability)

Latency Looks Like

Charts lag or show gaps. Sampling hides the slow tail.

Errors Look Like

Users complain while dashboards stay green. Traces break between layers.
