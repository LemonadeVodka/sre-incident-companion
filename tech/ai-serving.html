AI Serving & Capacity

Most AI latency and error incidents in the cloud come down to how the model is served: how many tokens go in and out, how much capacity you've reserved, and what happens when you run out. Learn these few ideas and the majority of incidents become understandable.

  • Latency ≈ time to first token + (output tokens × time per token). More input slows the start, and more output slows the finish.
  • Capacity is measured in tokens per minute. Exceed it and you get 429s, not slowness, unless a retry hides them.
  • Provisioned capacity buys predictability. Pay-as-you-go buys flexibility, but shares capacity with others.
  • Models have versions and retirement dates. A version change can change speed, length, and behavior with no code change.

Tokens

Models read and write tokens, chunks of text averaging about ¾ of an English word. Everything is counted in tokens: cost, quota, latency. A request has input tokens (system prompt + user prompt + retrieved context + conversation history) and output tokens (the answer).

Why This Matters to You

A prompt change that adds 2,000 tokens of context to every request can raise latency, cost, and quota usage all at once, while every service shows "healthy". Token counts per feature belong on the dashboard.

Streaming features (Ask Nimbus, Writing Assist) feel fast when TTFT is low, even if the full answer takes several seconds. Batch features (Catch Up, Next Step) care about total time and throughput.

Ask: "Is the P95 increase in time to first token, or in generation time? Did average input or output tokens change?"

Why AI Latency Is Long-Tailed

  • Output length varies widely. A 50-token answer and a 1,500-token answer can come from the same feature.
  • Shared capacity queues under load, so the slowest requests wait the longest.
  • Retries after 429s or timeouts add whole extra round trips.
  • Agentic flows chain several model calls (agents).

That's why the gap between P50 and P95 matters more for AI than for most web services. A widening gap is an early warning.

How 429s Work

  1. EstimateThe service estimates tokens for each request, including the maximum output requested, and counts them against the per-minute limit.
  2. RejectWhen the limit is reached it returns 429 Too Many Requests with a retry-after header, and remaining-tokens and remaining-requests headers.
  3. RetryClients and SDKs often retry automatically. That's good with backoff and jitter, but bad without them, because it turns throttling into a retry storm (deep dive).
The Hidden 429

If the gateway or SDK retries quietly, users see slowness, not errors. When P95 rises, always ask: "How many 429s did we get from the model, including retried ones?"

Setting max_tokens Too High Wastes Quota

Many services count the requested maximum output against the limit at request time. A feature that asks for 4,000 output tokens but uses 300 burns quota it never uses. It's a cheap fix that teams often miss.

Regional Capacity and Failover

  • Capacity is per region and per model. A popular new model may simply have no spare capacity in your region.
  • A secondary deployment in another region (behind the gateway) protects against regional outages and throttling, if it's tested and has quota.
  • Failover moves the load. The secondary needs enough quota to absorb it, or it fails too.
Ask: "If our primary region throttled for an hour, where would traffic go, does that region have the quota, and when did we last test it?"

Model Lifecycle

Hosted models have versions, and older versions have retirement dates. Deployments may be set to auto-upgrade to a new default version. A new version can be faster or slower, write longer or shorter answers, and behave differently with your prompts and filters.

  • Every production deployment pins a version, or someone owns the auto-upgrade decision.
  • There's a calendar of retirement dates per deployment, with an owner.
  • Upgrades go through evals, plus a canary for latency, output length, and errors (evals).

Cost

Cost scales with tokens. The main levers are shorter prompts, less retrieved context, capped output, caching, smaller models for simple tasks, and on-device handling (Nimbus's local-first design is also a cost strategy). Reliability incidents often have a cost signature: a fallback surge sends device work to the cloud and the bill spikes.

Go Deeper
  • KV cache: during decode the server keeps the attention state for each request in GPU memory. Long contexts use more of it, which limits how many requests fit at once.
  • Batching: serving systems batch requests together for efficiency. Under heavy load, batches get bigger and per-request latency rises.
  • Prompt caching: some services reuse the prefill work for repeated prompt prefixes, which cuts TTFT and cost. Put stable content (system prompts) first.
