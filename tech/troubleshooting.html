Troubleshooting Walkthrough

This is how your SREs investigate an AI incident when there's no runbook: find the layer, split the latency, read the error type, check what changed. Learn it so you can follow along, ask sharper questions, and recognize a strong investigation from a weak one. It covers AI latency, error rates, CDN errors, and 401s.

  • First answer which layer returned the error: edge, gateway, service, or model. One query compares all four.
  • Split P50/P95 latency by hop. First-token time up points to capacity or queueing. Total up with first token flat points to longer outputs.
  • CDN errors: read Front Door's error info and origin health. 401s: find which layer rejected the token, then which cohort.
  • For Rust services, know the signatures of runtime starvation, pool exhaustion, and panics.

Method When There's No Runbook

  1. Write the symptom down precisely."Device Care errors 9% since 14:05, 429 on chat-small." Precision rules out half the causes.
  2. Find the layer (next section).
  3. List 2–3 hypotheses in the channel, each with its cheapest test.
  4. Test the cheapest one first, unless another is far more likely.
  5. Mitigate as soon as one is plausible and the mitigation is reversible.
  6. Write down what worked. That's the start of the runbook.

Which Layer Returned the Error?

The same status code can come from different layers. This query counts errors at each layer for the same time window. Run it in the Log Analytics workspace that holds the Front Door and APIM logs and the workspace-based App Insights tables.

KQLErrors by layerEdge vs gateway vs backend vs services, side by side
// ── Parameters ─────────────────────────────
let window = 1h;                         // [TUNE] how far back to look
let fdCategory = "FrontDoorAccessLog";   // [AZURE] Front Door access log category
// ── Query ──────────────────────────────────
union
  (AzureDiagnostics
     | where TimeGenerated > ago(window) and Category == fdCategory
     | extend code = toint(column_ifexists("httpStatusCode_s", "")), w = 1, layer = "1 · edge (Front Door)"),
  (ApiManagementGatewayLogs
     | where TimeGenerated > ago(window)
     | extend code = toint(ResponseCode), w = 1, layer = "2 · gateway (APIM, to client)"),
  (ApiManagementGatewayLogs
     | where TimeGenerated > ago(window)
     | extend code = toint(BackendResponseCode), w = 1, layer = "3 · backend (as APIM saw it)"),
  (AppRequests
     | where TimeGenerated > ago(window)
     | extend code = toint(ResultCode), w = toint(ItemCount), layer = "4 · services (App Insights)")
| summarize total = sum(w), e5xx = sumif(w, code >= 500), e401 = sumif(w, code == 401),
            e403 = sumif(w, code == 403), e429 = sumif(w, code == 429) by layer
| order by layer asc
PatternPoints to
Edge 5xx high, gateway near normalFront Door can't reach APIM (origin connectivity, timeouts, origin health probes failing)
Edge 403 highWAF blocking. Check WAF logs for the rule.
Gateway 401 high, backend normalAPIM token validation: client tokens, an Entra problem, or a validate-jwt policy change
Backend 5xx (layer 3) matches services 5xx (layer 4)Our services are failing
Backend 5xx/504 high but services look fineNetwork or timeouts between APIM and services, or services crashing before logging (panics)
Services 5xx with Foundry dependency failuresThe model layer. See the error types below.

Decomposing Latency (P50 and P95)

Here is an illustrative P95 budget for a cloud-answered Writing Assist request. Learn the shape so you can spot which segment grew. On-device answers stop after the first segment, usually under a second.

KQLP50 / P95 per hop for one serviceModel vs retrieval vs our own code
// ── Parameters ─────────────────────────────
let role = "writing-assist-svc";                                          // [NIMBUS] cloud_RoleName of the service
let window = 1h;                                                          // [TUNE] how far back to look
let modelHosts = dynamic(["openai.azure.com", "services.ai.azure.com"]);  // [AZURE] Foundry hostnames
let retrievalHosts = dynamic(["search.windows.net"]);                     // [AZURE] AI Search hostnames
// ── Query ──────────────────────────────────
requests
| where timestamp > ago(window) and cloud_RoleName == role
| project operation_Id, request_ms = duration
| join kind=leftouter (
    dependencies
    | where timestamp > ago(window) and cloud_RoleName == role
    | extend hop = case(target has_any (modelHosts), "model",
                        target has_any (retrievalHosts), "retrieval", "other")
    | summarize hop_ms = sum(duration) by operation_Id, hop
  ) on operation_Id
| summarize p50_hop_ms = percentile(hop_ms, 50), p95_hop_ms = percentile(hop_ms, 95),
            p95_request_ms = percentile(request_ms, 95) by hop
| order by p95_hop_ms desc

To measure gateway overhead, compare APIM TotalTime with BackendTime in ApiManagementGatewayLogs. The difference is time spent in APIM itself, such as policies and token validation.

What you seeLikely cause
First token up, generation speed normalQueueing: PTU saturated, or traffic spilling to slower pay-as-you-go
First token up and input tokens upBigger prompts, so a slower start (more context, bigger retrieval chunks)
Total up, first token flat, output tokens upLonger answers after a prompt or model-version change
Request P95 up, every hop normalTime inside our Rust service. See Rust failure modes.
P50 fine, P95 upA subset is slow: one instance, one region, one client cohort, or long prompts
P50 and P95 both upSomething broad: model capacity, a dependency, or a deploy

Fallback surges are tricky because nothing on the server is broken. The cloud is just doing the device's work too. Mitigation usually means halting the local model rollout (Client CFT) and adding cloud capacity (Cloud Infrastructure).

Error Types: 429, 5xx, Timeouts

Timeout budgets should shrink as you go deeper: client 30 s → APIM 28 s → service-to-model 25 s → service-to-retrieval 2 s. If the client gives up before the service does, the server is doing wasted work.

CDN and Edge Errors (Front Door)

Edge errors happen before our code runs, so App Insights may show nothing at all. Use the Front Door logs.

KQLEdge errors by error type and routeWhy is Front Door failing?
// ── Parameters ─────────────────────────────
let window = 1h;                         // [TUNE] how far back to look
let fdCategory = "FrontDoorAccessLog";   // [AZURE] Front Door access log category
// ── Query ──────────────────────────────────
AzureDiagnostics
| where TimeGenerated > ago(window) and Category == fdCategory
| extend status = toint(column_ifexists("httpStatusCode_s", "")),
         errorInfo = tostring(column_ifexists("errorInfo_s", "")),
         route = tostring(column_ifexists("routeName_s", "")),
         pop = tostring(column_ifexists("pop_s", ""))
| where status >= 400
| summarize errors = count(), sample_pop = any(pop) by status, errorInfo, route
| order by errors desc
Error info / statusUsually meansCheck
OriginConnectionError, 502Front Door can't connect to the origin (APIM)APIM health, private link or DNS changes, origin certificate
OriginTimeout, 504The origin is too slowAPIM and service latency. Often model latency underneath.
503 with health probe failuresAll origins marked unhealthyThe health probe path and response, and origin group settings
403WAF blockWAF log category: which rule? Is it a new rule, or a client change that triggers it?
Errors at one POP onlyA regional edge problemAzure status. Mostly out of our control, so communicate.
Column names vary

Front Door log columns differ by tier and by diagnostic mode (AzureDiagnostics or resource-specific tables). The queries use column_ifexists() so they don't break, but check your own column names once and update the query. They're tagged [AZURE].

401 Investigation

  1. Which layer rejected the token?Use the layer query. A 401 at APIM means the client token was rejected. A 401 on the Foundry dependency means our service's managed identity was rejected.
  2. Which cohort?All clients point to the server side: Entra, APIM policy, or signing keys. One client version points to a client bug. A scattered small set of devices suggests clock skew.
  3. What changed?APIM policy edits, app registration changes, secret or certificate rotation, managed identity role assignments (AzureActivity).
  4. Is it the token refresh?A wave of 401s about an hour after a client release often means a token refresh bug in the new build.
KQL401s by client versionIs this one client build or everyone?
// ── Parameters ─────────────────────────────
let window = 6h;                         // [TUNE] how far back to look
let clientVersionKey = "client.version"; // [NIMBUS] attribute holding the desktop client version
// ── Query ──────────────────────────────────
requests
| where timestamp > ago(window)
| extend client = tostring(customDimensions[clientVersionKey])
| summarize total = sum(itemCount), unauthorized = sumif(itemCount, resultCode == "401") by client
| extend pct_401 = round(100.0 * unauthorized / total, 2)
| order by unauthorized desc

// ── Parameters ─────────────────────────────
let window = 6h;                         // [TUNE] how far back to look

dependencies
| where timestamp > ago(window) and resultCode in ("401", "403")
| summarize failures = sum(itemCount), first_seen = min(timestamp) by cloud_RoleName, target, resultCode
| order by first_seen asc
KQLToken validation errors in logsExpired vs not-yet-valid (clock skew) vs invalid
// ── Parameters ─────────────────────────────
let window = 6h;                                                                                 // [TUNE] how far back to look
let authPatterns = dynamic(["ExpiredSignature", "ImmatureSignature", "InvalidAudience", "AADSTS"]); // [TUNE] error strings your Rust JWT library / Entra emit
// ── Query ──────────────────────────────────
traces
| where timestamp > ago(window) and message has_any (authPatterns)

                     message has "InvalidAudience", "wrong audience (config?)",
                     "other auth error")
| summarize events = sum(itemCount) by kind, cloud_RoleName, bin(timestamp, 15m)

KQLRust panicsWhich instance, how often, what message
// ── Parameters ─────────────────────────────
let role = "writing-assist-svc";   // [NIMBUS] cloud_RoleName of the service
let window = 6h;                   // [TUNE] how far back to look

union traces, exceptions
| where timestamp > ago(window) and cloud_RoleName == role
| extend text = coalesce(message, outerMessage)
| where text has "panicked at"
| summarize panics = count(), sample = any(text) by cloud_RoleInstance, bin(timestamp, 15m)
| order by timestamp desc

What Changed?

KQLWho changed what in AzureAPIM policies, Front Door, role assignments, deployments
// ── Parameters ─────────────────────────────
let window = 24h;                                                   // [TUNE] how far back to look
let resourceGroups = dynamic(["rg-nimbus-prod", "rg-nimbus-ai"]);   // [NIMBUS] your production resource groups
// ── Query ──────────────────────────────────
AzureActivity
| where TimeGenerated > ago(window) and ResourceGroup in~ (resourceGroups)
| where CategoryValue == "Administrative" and ActivityStatusValue in ("Success", "Succeeded")
| project TimeGenerated, Caller, OperationNameValue, ResourceGroup, Resource = tostring(split(_ResourceId, "/")[-1])
| order by TimeGenerated desc

Also check service deploys (version first seen), desktop client rollouts (by client version), and prompt or model-version changes, which you'll have to ask the CFT about because they often aren't logged.
