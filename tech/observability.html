Observability for AI

You can't run what you can't see, and AI products need a few signals traditional services don't: tokens, model versions, finish reasons, retries against quota, and the split between device and cloud. This module tells you what good looks like and what to ask your team to build.

  • One trace across all layers (device → edge → gateway → orchestrator → retrieval → model) is the single most valuable investment.
  • Model calls need AI-specific attributes: model and version, input and output tokens, finish reason, and status, using the OpenTelemetry GenAI conventions.
  • Sampling can hide incidents. Know what's sampled and how.
  • Demand five dashboards, each owned by someone.

Traces Across Layers

A trace follows one request through every service. Each step is a span with a duration and status. With traces, "which layer is slow?" takes one query (decomposing latency). Without them, every incident becomes a debate between teams.

  • Trace context propagates across every hop, including the gateway and partner calls.
  • The device client starts the trace, or at least sends a request ID the cloud records.
  • Model calls, retrieval, and tool calls are separate spans.
  • Retries are visible as separate spans, not hidden inside one.

GenAI Semantic Conventions

OpenTelemetry defines standard attribute names for generative AI calls, so every team's telemetry looks the same. The ones to insist on:

AttributeWhy you care
gen_ai.operation.nameChat, embeddings, and so on, to separate model call types
gen_ai.request.model / gen_ai.response.modelWhich model and version actually answered. Catches silent upgrades.
gen_ai.usage.input_tokens / gen_ai.usage.output_tokensExplains latency, cost, and quota changes
gen_ai.response.finish_reasonsStop, length limit, or content filter: quality and safety signals
error.typeGroups failures, for example 429 vs timeout vs 400

The conventions are still evolving, so the exact names may change. The point is consistency across teams.

Privacy

Prompt and answer content is often sensitive, and Nimbus's local-first design promises users privacy. Record counts and metadata by default, and only capture content with explicit approval.

Sampling

  • Head sampling keeps a fixed percentage of traces, decided at the start. It's cheap, but may drop the rare failing requests you need.
  • Adaptive sampling (common in Application Insights) lowers the rate as volume rises. Counts need adjusting, or charts under-report during peaks.
  • Tail sampling (in an OpenTelemetry collector) decides after the request finishes, keeping all errors and slow requests. It's best for incidents, but costs more to run.
Ask: "What's our sampling rate during peaks, and do we keep 100% of errors and slow requests?"

Dashboards to Demand

1. Feature Health

P50, P95, and error rate per feature, against last week and the SLO. This is the NOC's home screen.

2. Layer Breakdown

Errors and latency by layer: edge, gateway, orchestrator, retrieval, model, partner.

3. Model Capacity

TPM used vs quota, 429s (including retried), TTFT, and tokens per request per deployment.

4. Device & Sync

Local vs cloud split, fallback rate, client versions, relay success and sync lag.

5. Partners

Success rate and latency per partner and per integration platform connector.
