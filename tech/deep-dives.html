Technical Corner · How Your SREs Work

Deep Dives

The hardest Nimbus incidents aren't single broken components. They come from interactions: shared quota, feedback loops, biased telemetry, and models that change underneath you. This page is about reasoning at the system level.

  • Shared Foundry deployments create noisy neighbors. Isolate interactive traffic from background traffic.
  • Retries without backoff turn a blip into an outage. Look for feedback loops.
  • Your telemetry can be biased by sampling and broken propagation. Know what you can't see.
  • Models are dependencies that change: version upgrades and prompt changes are deploys.

Thinking in Systems

  • Contributing factors, not one root cause. Complex incidents usually need several conditions at once, for example a batch job, a shared deployment, retries without backoff, and no alert on 429s.
  • Write hypotheses down. In the incident channel, list each hypothesis, the evidence for and against it, and the cheapest test. This avoids tunnel vision and lets others help.
  • Test the cheapest hypothesis first, unless an expensive one has much higher odds. Pausing a batch job is cheaper than reading code.
  • Beware of confirmation bias. Ask "what would I expect to see if I'm wrong?", then look for it.

Noisy Neighbor on Shared Foundry Quota

Foundry quota is counted per deployment in tokens per minute and requests per minute. PTU deployments have a fixed throughput. When several CFTs share a deployment, the heaviest caller sets everyone else's experience.

Classic Nimbus pattern: at 09:00 local time, Next Step starts its morning batch on chat-small. Its token usage triples. Device Care is interactive and shares chat-small, and it starts getting 429s. Device Care's retries add more load. Users see "Nimbus is having trouble right now."

  1. Prove it.Run token consumption by caller as a stacked chart. One caller's band grows just before the 429s start.
  2. Mitigate.Pause or rate-limit the background caller, through a feature flag or APIM policy.
  3. Fix it structurally.Separate deployments for interactive and background traffic. Add per-caller token limits at APIM. Use priority-based routing so interactive calls go to PTU first.
  4. Alert on it.Alert on a deployment's tokens per minute as a share of quota (saturation), not only on 429s (failure).

Local-to-Cloud Fallback Surge

The device orchestrator normally answers a large share of simple requests on-device. If a local model update ships with a bug, or a driver update breaks the NPU, millions of devices quietly start sending those requests to the cloud. This is a demand shock with no server-side cause.

  1. Spot it.Cloud request volume and tokens per minute rise in a staircase that follows the client or local model rollout curve, not the time of day.
  2. Prove it.The fallback rate by local model version jumps, and the local share drops for the new version.
  3. Mitigate on both sides.The Client CFT halts the rollout or reverts the local model. Cloud Infrastructure adds spillover and sheds background load (Next Step) to absorb the surge.
  4. Fix it structurally.Make fallback rate a rollout health gate. Cap how much fallback traffic the cloud will accept per client version. Alert on local share as well as server errors.
Why It's Easy to Miss

Server dashboards show more traffic, not errors, so the first symptom is usually 429s in an unrelated feature that shares a deployment. The cloud teams and the Client CFT each see half of the picture.

Retry Storms and Cascading Failure

Signs: calls per operation rising (retry detector), traffic to Foundry growing faster than user requests, and recovery that doesn't happen after the original trigger is gone.

Retry amplification: if the client, APIM, and the orchestration service each retry 3 times, one user action can turn into 4 × 4 × 4 = 64 model calls. Retry at one layer only, usually the one closest to the dependency.

Mitigate: shed load first (pause background features, rate-limit at APIM), so the loop has room to drain. Then fix the retry policies.

The Cloud Orchestrator as a Choke Point

Every cloud request passes through the cloud orchestrator, which Cloud Infrastructure owns. When it slows down, every feature slows down together, while Foundry and the feature services look normal from the inside. Recognize the pattern (everything degrades at once, and the dependencies are fine) and bring Cloud Infrastructure in early with the evidence. Their structural fixes are horizontal scaling, per-feature bulkheads (so one feature can't exhaust the router), and canary releases for routing changes.

Tail Latency

For LLM workloads the P95 is often 2–4× the P50, because output length varies a lot. And P95 still hides the slowest 5%. Tail latency matters more than it seems:

  • Fan-out multiplies it. If one action makes 5 model calls in sequence (as Device Care's tool loop does), the chance that at least one of them lands in its own slowest 5% is about 23%.
  • Heavy users live in the tail. Long documents and long meetings produce the largest prompts, and the users who send them tend to be your most engaged.
  • Levers: cap max_tokens to what the feature really needs, stream every interactive response, trim context (summarize history, rank retrieval chunks), and use the small model where quality allows. For idempotent, cheap calls, consider hedged requests.

Sampling Bias and Broken Trace Propagation

Your telemetry isn't the truth. It's a sample, and the sample can be biased.

Fixed-rate sampling at 10%Rare failures and slow outliers are under-represented or missingCount with sum(itemCount). Use tail-based sampling in an OTel Collector to keep all errors and slow traces.

Reality check: survivorship bias

Server-side success rates only count requests that reached the server. If the client can't connect, the server's error rate stays perfect. "Dashboards green, users complaining" is often exactly this. See the playbook.

Regional Failover

Nimbus has Foundry deployments in East US 2 (primary) and Sweden Central (secondary). Failover is a Cloud Infrastructure decision, made with these trade-offs in mind:

  • Capacity: can the secondary absorb the traffic? Check its quota and PTU headroom first, or you'll cause a second incident.
  • Data residency: some users' data may be required to stay in-region. Confirm which features can move.
  • Model parity: are the same model versions and content-filter settings deployed in both regions?
  • Latency: cross-region calls add network time. Is that acceptable for interactive features?
  • Mechanism: APIM backend pool or routing policy change. Is it tested? When did you last run it in a game day?
  • Failback: decide on the criteria for coming back before you leave.

Prompt and Model Regressions

In LLM systems, prompts, model versions, and content-filter configurations are code. They can regress latency, cost, quality, and safety behavior without a single line of service code changing.

ChangeTypical symptomDetection
Prompt template adds contextInput tokens up, TTFT up, 429s soonerToken growth step change
Model version auto-upgradeOutput length changes, different latency, different filter behaviorGroup metrics by the response model attribute or version, and check the deployment's version history
Content filter policy changeSpike in blocked responses for one featureContent-filter query
Tool or function schema changeDevice Care tool-call failures, more model turns per taskCalls per operation, exceptions in tool parsing
Quality regressionNo errors, but users give thumbs-down or abandonOffline evals, feedback events, task-completion rate

Prevent it: pin model versions in production, put prompt templates behind flags and version them, run evaluation suites before rollout, and canary model changes on a small slice of traffic.

Capacity Planning

  • Plan in tokens, not requests. Expected requests × (average input tokens + average output tokens) at the peak minute, per deployment.
  • Plan for the peak minute, not the daily average. Desktop usage spikes at the start of the workday in each timezone.
  • Keep headroom. Target at most 70–80% of PTU utilization at peak, so bursts and failover traffic fit.
  • Track demand drivers: client install base growth, new feature launches, and prompt growth (which is easy to miss).
  • Review quarterly with every CFT. A CFT launch that doubles token use is a capacity event.

Game Days

Practice the incidents you expect, before they happen. Each game day should test a hypothesis such as "if X happens, we detect it in under 5 minutes and mitigate in under 15".

Throttle chat-small

Lower its quota in staging. Do the alerts fire? Does Device Care degrade gracefully?

Fail East US 2

Block the primary Foundry endpoint. Can Cloud Infrastructure fail over within the target time?

Kill Telemetry

Stop the exporter in one service. Does anyone notice? How long does it take?

Bad Prompt Deploy

Ship a prompt that doubles the input tokens. Does anything catch it before the 429s do?
