NOC · First line of defense

Pre-approved actions

CFTs don't always respond quickly. When users are affected and the owner hasn't responded, the NOC may take a short list of low-risk, reversible actions without waiting. This page lists them, with how to undo each one.

  • An action is allowed only if it's on this list, user impact is confirmed, and the owner hasn't responded within the timer (or SRE asks you).
  • Announce before you act, and record after. Take one action at a time.
  • Everything else (rollbacks, failover, quota, WAF, content filters) belongs to SRE or Platform.

The rules

  1. Impact is confirmed.A query shows user impact above baseline, not just an alert.
  2. The owner hasn't responded within the timer (15 minutes for Sev 2, 5 minutes for Sev 1), or SRE or the owner asked you to act.
  3. The action is on this list, and the "use when" conditions match.
  4. Announce it in the incident channel (template below), then act.
  5. Record it in the pinned record, with the time and how to undo it, and tell SRE.
  6. Verify within 10 minutes. If it didn't help, or made things worse, undo it.

Why: [impact numbers]; [owner] paged HH:MM, no ack.

Approved actions

Pause the Proactive Tips background batch

NOC approvedRisk: low (tips arrive late)
Use when
429s or high latency on chat-small are hurting Device Care, and the Proactive Tips batch is running.
How
Feature flag service: set proactive_tips.batch_enabled to false. This is a Nimbus-specific flag, so use your own equivalent.
Undo
Set the flag back to true. The batch resumes from its queue.
Notify
Insights CFT (Slack) and SRE.

Halt a desktop client staged rollout

NOC approvedRisk: low (delays a release)
Use when
Errors, 401s, or crashes are concentrated in the client version that is currently ramping.
How
Release dashboard: select the ramping version and click Pause ramp. Users who already have it keep it.
Undo
Click Resume ramp. Only resume once the Client CFT confirms a fix.
Notify
Client CFT, release manager, and SRE.

Restart one unhealthy service instance

NOC approvedRisk: low, one at a time
Use when
A single instance fails health checks or shows much higher latency than its peers (a typical Rust async runtime stall), and the others are healthy.
How
Restart one instance from the hosting portal. Wait for it to report healthy before considering another.
Undo
None needed. If all instances look unhealthy, stop: that's not an instance problem, so page SRE.
Notify
The owning CFT and SRE. Save the instance name for the investigation.

Scale out a service by a small step

NOC approvedRisk: low (cost)
Use when
A service's CPU or request queue is saturated on every instance, and its dependencies (model, retrieval) look healthy.
How
Increase the instance count by up to +50%, staying within the documented maximum for that service.
Undo
Return to the previous count once the incident is resolved.
Notify
The owning CFT and SRE. Don't scale out if 429s are the problem, because more instances mean more model calls.

Turn on the in-app "degraded service" banner

NOC approved (Sev 1–2)Risk: low
Use when
A Sev 1–2 is declared and users are visibly affected. Use the pre-written text only.
How
Server-driven message config: enable service_banner with the approved "Some features are slower than usual" text for the affected feature.
Undo
Disable the banner when the incident is resolved.
Notify
The IC and the senior manager. Custom wording requires manager approval.

Not pre-approved: ask SRE or Platform

ActionWhy it needs SRE or Platform
Rolling back a service deploymentCan conflict with data or config changes, and needs the owner's context.
Region failover (Front Door origin or Foundry)Capacity, data residency, and cost implications.
Quota, PTU, or spillover changesCost, and affects every CFT.
WAF rule changesSecurity risk.
Rotating secrets or keys, or changing APIM auth policiesCan cause a wider 401 outage if done wrong.
Content filter changesResponsible-AI policy owners must approve.
Purging the CDN cacheCan overload the origin.
Adding to this list

New actions get added after an incident shows they're safe and useful. The SRE lead and the owning CFT both sign off, and each one is documented here with its undo steps.
