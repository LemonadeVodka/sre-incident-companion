Nimbus KQL

Copy-ready queries for Nimbus incidents. Every value that's specific to Nimbus is highlighted and gathered at the top of each query, so adapting it to a real environment means changing a few lines. You don't have to rewrite the query.

  • Each query starts with a parameter block. The query body below it is generic KQL.
  • Amber = [NIMBUS]: invented for this scenario, so you must change it. Dotted = [TUNE]: adjust it to your data. [AZURE] values are real schema, so keep them.
  • Set your own names once in Make it yours, and every query on the site updates.
  • For generic queries that work in any Azure environment, use the KQL toolkit repo.
  • New to KQL? Start with KQL Training.
Applies Anywhere

The parameter-block convention works in any query language: keep everything environment-specific at the top and the logic below. For vendor-neutral KQL, use the KQL toolkit.

How to Read These Queries

KQLAnatomy of a queryChange the top block; leave the body alone
// ── Parameters ─────────────────────────────
let role = "writing-assist-svc";         // [NIMBUS] your service's cloud_RoleName
let featureKey = "feature.experience";   // [NIMBUS] your custom attribute key
let modelHosts = dynamic(["openai.azure.com"]);  // [AZURE] real Azure hostname, usually keep
let window = 1h;                         // [TUNE] time range for your data
// ── Query ──────────────────────────────────
requests
| where timestamp > ago(window) and cloud_RoleName == role
| summarize p50 = percentile(duration, 50), p95 = percentile(duration, 95)
TagMeaningHow to find your real value
[NIMBUS]Invented for this scenario. Must change.Service names: requests | distinct cloud_RoleName. Attribute keys: requests | take 5 | project customDimensions.
[TUNE]Real, but depends on your trafficWiden windows for low-traffic services. Base thresholds on last week's normal.
[AZURE]Real Azure or OpenTelemetry schemaUsually keep. Verify Front Door column names once, because they vary by tier.

Latency (P50 / P95)

KQLP50 / P95 by feature, now vs yesterdayWhich feature got slower, and by how much?
// ── Parameters ─────────────────────────────
let window = 1h;                         // [TUNE] how far back to look
let featureKey = "feature.experience";   // [NIMBUS] custom attribute holding the feature name
// ── Query ──────────────────────────────────
requests
| where timestamp > ago(window) or timestamp between (ago(1d + window) .. ago(1d))
| extend period = iff(timestamp > ago(window), "cur", "base")
| extend feature = coalesce(tostring(customDimensions[featureKey]), cloud_RoleName)
| summarize p50_ms = percentile(duration, 50), p95_ms = percentile(duration, 95) by feature, period
| evaluate pivot(period, any(p95_ms))
| extend p95_ratio = round(todouble(cur) / todouble(base), 2)
| order by p95_ratio desc
KQLP50 / P95 over time for one serviceWhen did it start? Getting better or worse?
// ── Parameters ─────────────────────────────
let role = "writing-assist-svc";   // [NIMBUS] cloud_RoleName of the service
let window = 6h;                   // [TUNE] how far back to look
let step = 5m;                     // [TUNE] bucket size
// ── Query ──────────────────────────────────
requests
| where timestamp > ago(window) and cloud_RoleName == role
| summarize p50 = percentile(duration, 50), p95 = percentile(duration, 95) by bin(timestamp, step)
| render timechart
KQLDependency P50 / P95 by targetWhich downstream call got slower?
// ── Parameters ─────────────────────────────
let role = "writing-assist-svc";   // [NIMBUS] cloud_RoleName of the service
let window = 1h;                   // [TUNE] how far back to look
// ── Query ──────────────────────────────────
dependencies
| where timestamp > ago(window) and cloud_RoleName == role
| summarize calls = sum(itemCount), p50_ms = percentile(duration, 50), p95_ms = percentile(duration, 95),
            failed = sumif(itemCount, success == false) by target, type
| order by p95_ms desc

For a per-hop split of one request (model vs retrieval vs our own code), see P50/P95 per hop.

Device and Routing

The device orchestrator answers some requests on-device and sends the rest to the cloud. These queries read client telemetry, which is the only place the local path shows up.

KQLLocal vs Cloud Answers by Client VersionIs the device orchestrator sending more to the cloud than usual?
// ── Parameters ─────────────────────────────
let window = 24h;                        // [TUNE] how far back to look
let routingEvent = "routing.decision";   // [NIMBUS] client event emitted by the device orchestrator
let routeKey = "route";                  // [NIMBUS] attribute: "local" or "cloud"
let clientVersionKey = "client.version"; // [NIMBUS] attribute holding the desktop client version
// ── Query ──────────────────────────────────
customEvents
| where timestamp > ago(window) and name == routingEvent
| extend route = tostring(customDimensions[routeKey]), client = tostring(customDimensions[clientVersionKey])
| summarize local_pct = round(100.0 * sumif(itemCount, route == "local") / sum(itemCount), 1)
    by client, bin(timestamp, 1h)
| render timechart
KQLLocal-to-Cloud Fallback Rate and ReasonsIs on-device inference failing and pushing load to the cloud?
// ── Parameters ─────────────────────────────
let window = 24h;                          // [TUNE] how far back to look
let routingEvent = "routing.decision";     // [NIMBUS] client event emitted by the device orchestrator
let fallbackKey = "fallback.reason";       // [NIMBUS] attribute set when a local attempt fell back to cloud
let localModelKey = "local_model.version"; // [NIMBUS] attribute holding the on-device model version
// ── Query ──────────────────────────────────
customEvents
| where timestamp > ago(window) and name == routingEvent
| extend reason = tostring(customDimensions[fallbackKey]), model = tostring(customDimensions[localModelKey])
| summarize decisions = sum(itemCount), fallbacks = sumif(itemCount, isnotempty(reason)),
            top_reasons = make_set_if(reason, isnotempty(reason), 5) by model, bin(timestamp, 1h)
| extend fallback_pct = round(100.0 * fallbacks / decisions, 2)
| order by timestamp desc, fallback_pct desc

// ── Parameters ─────────────────────────────

SLOs

KQLMulti-window burn rate for one serviceAre we burning error budget fast enough to page?
// ── Parameters ─────────────────────────────
let role = "writing-assist-svc";   // [NIMBUS] cloud_RoleName of the service
let slo = 0.995;                   // [TUNE] your availability target
// ── Query ──────────────────────────────────
let err_rate = (w: timespan) {
    requests
    | where timestamp > ago(w) and cloud_RoleName == role
    | summarize bad = sumif(itemCount, success == false), total = sum(itemCount)
    | project rate = todouble(bad) / todouble(total)
};
let b1h  = toscalar(err_rate(1h))  / (1 - slo);
let b5m  = toscalar(err_rate(5m))  / (1 - slo);
let b6h  = toscalar(err_rate(6h))  / (1 - slo);
let b30m = toscalar(err_rate(30m)) / (1 - slo);
print burn_1h = round(b1h, 1), burn_5m = round(b5m, 1), burn_6h = round(b6h, 1), burn_30m = round(b30m, 1)
| extend page_fast = burn_1h > 14.4 and burn_5m > 14.4, page_slow = burn_6h > 6 and burn_30m > 6

See Fundamentals → burn-rate alerts for where these thresholds come from.
